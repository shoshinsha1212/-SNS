# 03 AIパイプライン

## 基本方針

1. **AIは「下書き」と「整理」の係**：判定（どの原則が共通原則か等）は [02](./02_アルゴリズム.md) の数値ルールで行い、AIはその結果を文章にする。
2. **AIが作った原則は、必ず投票を経る**：AIの文章が投票なしに成果物に載ることはない。
3. **本人確認を挟む**：不満から原則への変換、体験談の匿名化は、必ず投稿者本人が確認・修正してから公開する。
4. **出力はJSONで受け取る**：アプリ側で検証できるよう、すべてのプロンプトは決まった形のJSONを返させる。
5. **引用IDを必須にする**：成果物の文章は、根拠となる原則・体験談のIDを必ず添えさせ、存在しないIDがあれば再生成する（でっち上げ防止）。

## パイプライン一覧

| # | 名前 | 入力 | 出力 | 実行のタイミング |
|---|------|------|------|------------------|
| P1 | 不満・体験 → 原則の変換 | 自由記述 | 原則の候補（1〜3件）＋体験談の下書き | 投稿時（本人がその場で確認） |
| P2 | 重複の判定 | 新しい原則＋似ている既存の原則 | 統合するかどうか | 投稿時 |
| P3 | 立場の軸の提案 | トピックの説明 | 軸と選択肢 | トピック作成時 |
| P4 | 体験談の匿名化・要約 | 体験談の本文 | 匿名化した本文、要約 | 投稿時（本人が確認） |
| P5 | 条件付き合意案の生成 | 分岐点＋両側の体験談＋境界人の体験談 | 新しい原則の候補 | 分岐点ができたとき |
| P6 | 成果物の文章化 | セクション分類の結果＋統計＋体験談 | Markdownの本文＋引用ID | セクション分類が変わったとき |
| P7 | 規約チェック | 投稿 | 判定と理由 | 投稿時 |

## P1 不満・体験 → 原則の変換

いきなり「原則を書いてください」と言われても書けない人のための、入口の機能です。

```text
あなたは、市民の声を「投票できる原則」に整える編集者です。

# トピック
{topic.title}：{topic.description}

# 参加者の投稿（自由記述）
{user_input}

# 作業
1. 投稿から、参加者が「こうあってほしい／こうあってほしくない」と考えていることを読み取る。
2. それを、他の人が賛成・反対を表明できる「原則」の形に書き直す。
   - 1文、80字以内、「〜すべきだ」「〜してほしい」「〜してはならない」のいずれかで終える
   - 投稿者の主張を弱めたり強めたりしない。特定の人・団体への攻撃は除く
   - 1つの原則に複数の主張を入れない（必要なら分けて最大3件）
3. 投稿の中の具体的な出来事は、原則ではなく「体験談の下書き」として分けて残す。
4. 原則にしにくい投稿（愚痴だけで主張がない等）は、無理に作らず needs_clarification を true にし、参加者への問いかけを1つ書く。

# 出力（JSONのみ）
{
  "principles": [{"text": "...", "type": "should|should_not|want"}],
  "story_draft": {"kind": "past|present|future", "text": "..."} | null,
  "needs_clarification": false,
  "clarifying_question": null
}
```

**画面での扱い**：候補を「この原則で投稿する／直して投稿する／やめる」の3択で見せる。原則と体験談は自動で紐づける（`stance = supports`）。

## P2 重複の判定

1. 新しい原則の埋め込みベクトルで、既存の原則から類似度の高い上位5件を探す。
2. 類似度が0.85未満なら重複なしとして公開する。0.85以上ならAIに判定させる。

```text
次の「新しい原則」が「既存の原則」のどれかと実質的に同じ主張かを判定してください。
- 同じ：言い回しが違うだけで、賛成する人と反対する人がほぼ同じになると考えられる
- 違う：条件・範囲・強さが違い、賛否が分かれうる（例：「禁止すべき」と「制限すべき」は違う）

新しい原則：{new}
既存の原則：{candidates（ID付き）}

出力（JSONのみ）：{"duplicate_of": "ID" | null, "reason": "..."}
```

> [!TIP]
> 「違い」を残すほうに倒します。条件や範囲の違いこそ、立場による差が出やすい部分だからです。

## P3 立場の軸の提案

```text
次のトピックについて、参加者の意見が「立場や利害」によって分かれそうな軸を提案してください。

# トピック
{topic.title}：{topic.description}

# 条件
- 軸は2〜3本。各軸の選択肢は2〜6個で、誰もがどれか1つを選べるようにする（「当てはまらない」を必ず含める）
- 軸は「このテーマとの関わり方（作る・使う・規制する・影響を受ける等）」を最優先にする
- 思想・信条・政党支持・宗教・病歴など、要配慮個人情報にあたる軸は提案しない
- 年代・職業分類など基本属性で足りる軸は提案しない（すでに別に持っている）

# 出力（JSONのみ）
{"axes": [{"name": "...", "options": ["...", "..."], "why_divergent": "この軸で意見が分かれそうな理由"}]}
```

運営またはトピック作成者が確認して確定する。トピック開始後の軸の追加はできるが、既存の票には立場が記録されないため、分析は新しい票からになる。

## P4 体験談の匿名化・要約

```text
次の体験談から、本人や第三者を特定できる情報を伏せてください。
- 伏せるもの：固有名詞（人名・学校名・会社名・地名）、具体的な日付、珍しい役職名など
- 伏せ方：[学校名]のような角括弧に置き換える。意味が通るよう最小限に言い換えてもよい
- 体験の中身・感情・主張は変えない
あわせて、80字以内の要約を作ってください。

体験談：{story.body}

出力（JSONのみ）：{"masked_body": "...", "summary": "...", "masked_items": ["伏せた内容の種類"]}
```

本人が「伏せた結果」を確認してから公開する。本人が伏せる前の文章を選んだ場合も、公開範囲は本人の選択に従う。

## P5 条件付き合意案の生成

分岐点ができたとき、対立する双方が受け入れられそうな**新しい原則の候補**を作り、投票にかけます。

```text
次の原則は、立場によって賛否が大きく分かれています。

# 原則
{statement.text}
# 立場ごとの賛成率
{立場: 賛成率 の一覧}
# 賛成側の体験談（代表3件）
{...}
# 反対側の体験談（代表3件）
{...}
# 自分の立場の多数派と逆の票を入れた人の体験談
{...}

# 作業
双方の体験談に書かれた「懸念」と「大事にしているもの」をそれぞれ1文で整理し、
両方の懸念に応える条件をつけた原則を最大3件作ってください。
- 1文、80字以内
- 元の原則の単なる言い換えや、中身のない妥協（「よく話し合うべき」等）は作らない
- 体験談に根拠のない条件を作らない

# 出力（JSONのみ）
{
  "concerns": {"support_side": "...", "oppose_side": "..."},
  "bridge_principles": [{"text": "...", "grounded_in_story_ids": ["..."]}]
}
```

- 生成した原則は `origin = ai_bridge` として通常の原則と同様に投票にかける。画面には「AIが提案した条件付きの原則」と明示する。
- 成果物の③に入れるかは、投票の結果だけで決める（[02 の 2.9](./02_アルゴリズム.md#29-成果物のセクション分類)）。

## P6 成果物の文章化

```text
あなたは、市民の議論の結果をまとめる報告書の書き手です。
次のデータだけを使って、成果物の本文を書いてください。

# トピック
{topic}
# 分析の条件
参加者数、期間、閾値（{params}）
# セクションごとの原則と統計
{①〜⑤の原則（ID・本文・立場ごとの賛成率・ギャップ）}
# 引用してよい体験談
{ID・要約・書き手の立場・種類}

# 書き方
- 構成：はじめに（参加者と方法）→ ①立場を越えた共通原則 → ②立場による分岐点
  → ③条件付き合意案 → ④立場によらず意見が割れている論点 → この成果物の限界
- ②では、原則ごとに「どの立場がどう考え、その背景にどんな体験があるか」を、
  双方を同じ分量・同じ敬意で書く。どちらが正しいかは書かない
- 「ポジショントーク」「利己的」など、立場の違いを動機の問題として決めつける表現は使わない
- 数字は与えられたものだけを使う。体験談は要約の範囲で言い換え、必ずIDを添える
- 「この成果物の限界」には、参加者の偏り（自由参加であること、立場ごとの人数）を必ず書く

# 出力（JSONのみ）
{"body_md": "...", "citations": [{"section_key": "...", "ref_type": "statement|story", "ref_id": "..."}]}
```

**生成後の自動チェック**
- `citations` のIDがすべて実在し、そのセクションで渡したものかを確認する。
- 本文中の数字が、渡した統計に含まれているかを確認する。
- 不合格なら1回だけ再生成し、それでも不合格なら前のバージョンを維持して運営に通知する。

## P7 規約チェック

- まず専用のモデレーションAPIで明らかな違反（脅迫、差別的な攻撃、個人情報の暴露）を判定する。
- 判定が微妙なものは人間の運営が確認する。
- 「意見が過激」「少数意見」というだけでは削除しない。削除理由は投稿者に通知し、削除件数と理由の分類は定期的に公開する（運営の透明性）。

## モデルの使い分け（目安）

| パイプライン | 求める性質 | 目安 |
|--------------|------------|------|
| P1, P2, P4, P7 | 速さ・安さ（投稿のたびに動く） | 小型モデル |
| P3, P5, P6 | 文章の質・公平さ（頻度は低い） | 大型モデル |
| 埋め込み | 日本語の意味の近さ | 多言語の埋め込みモデル |

## 評価の方法

- **P1**：投稿者が「直さずにそのまま使った」割合、「やめた」割合を記録する。
- **P5**：AI提案の原則が③に入った割合。
- **P6**：各立場の参加者に「自分の立場の考えが公平に書かれているか」を5段階で聞き、立場ごとの平均に差がないかを見る（書き方の偏りの検出）。
